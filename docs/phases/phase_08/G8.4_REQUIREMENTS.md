### 1. Executive Overview & Scope

In distributed transactional workflow platforms, the API ingestion boundary is the primary point of external pressure. It must withstand:
1. Massive multi-producer ingestion storms without dropping requests or corrupting transactions.
2. Concurrent idempotency storms where thousands of parallel threads submit the exact same idempotency key simultaneously (e.g., automated retries or network replays).
3. Adversarial and edge-case API client behaviors (malformed payloads, boundary conditions, invalid lifecycle state transitions).
4. Resource exhaustion events (such as database connection pool saturation).
5. Transactional consistency guarantees between primary application tables (`tasks`) and downstream delivery mechanisms (`outbox_events`).

Milestone **G8.4** establishes, validates, and stresses the API ingestion layer, transactional outbox pattern, idempotency engine, and database connection pooling under high concurrency.

The central validation question is:
> **Can TaskForge maintain strict serializability, zero duplicate task creation, 100% transactional outbox integrity, and deterministic error responses under heavy concurrent producer storms and database connection pressure?**

---

### 2. Core Functional & Architectural Invariants

The ingestion layer and persistence subsystems must enforce the following invariants:

1. **Strict Idempotency Uniqueness (At-Most-Once Creation):** Regardless of concurrency level (from 1 to 1,000 concurrent producers), submissions bearing the same `idempotency_key` and identical payload must produce exactly one logical task in the database (`tasks` table) and exactly one corresponding `outbox_events` record. All concurrent callers must receive the identical task ID with HTTP 201 (initial creator) or HTTP 200 (deduplicated).
2. **Idempotency Payload Collision Detection:** If an `idempotency_key` is reused with a conflicting payload, task type, or configuration, the system must reject the request with HTTP 409 Conflict (`IDEMPOTENCY_CONFLICT`) and make zero modifications to the existing task.
3. **100% Transactional Outbox Accountability:** Every task inserted into `tasks` must atomically commit an accompanying event in `outbox_events` within the identical database transaction. There must be zero orphaned tasks without outbox events, and zero orphaned outbox events without tasks.
4. **Deterministic API State Machine Protection:** State mutations requested via the API (cancellations, retries) must strictly adhere to the state transition matrix. Non-existent IDs must return HTTP 404; invalid transitions must return HTTP 409 Conflict; malformed schemas must return HTTP 422 Unprocessable Entity.
5. **Connection Pool Resilience:** When client concurrency exceeds the database connection pool capacity (`pool_size + max_overflow`), connections must be cleanly queued until the timeout expires. Once load recedes, the pool must self-heal to an idle state with zero leaked connections and zero need for service restarts.

### 3. Detailed Gate Requirements

```
                       Ingestion & Idempotency Architecture
                       
   [Concurrent HTTP Clients] (100 - 1,000 producers)
               │
               ▼
   [FastAPI Ingestion Boundary] (Validation: 422 on schema violation)
               │
               ▼
   [TaskService.submit_task()]
        │
        ├─► [Idempotency Pre-Check] ──(Hit with different payload)──► HTTP 409 Conflict
        │
        ▼
   [Atomic DB Transaction] (PostgreSQL 16)
        ├─► INSERT INTO tasks (idempotency_key UNIQUE)
        │     └─► [On Collision]: Catch (IntegrityError, SQLAlchemyError) -> ROLLBACK -> Fetch Existing
        │
        ├─► INSERT INTO outbox_events (aggregate_id = task.id, event_type = "task.created")
        │
        ▼
   [Commit Transaction] (Atomically commits task + outbox event)
```

#### Gate G8.4.1: API Contract & Edge-Case Resilience
* **Requirement:** Exhaustively audit and verify all API endpoints and boundary behaviors:
  - `POST /api/v1/tasks`: Valid task creation returns HTTP 201; malformed schemas (missing fields, priority < 1 or > 4, negative retries, non-JSON body) return HTTP 422 with structured validation errors.
  - `GET /api/v1/tasks/{task_id}`: Existing task returns HTTP 200; non-existent UUID or malformed identifier returns HTTP 404.
  - `GET /api/v1/tasks`: Paginated list endpoint supports `limit` (1..100) and `offset` (>=0), filtering by `status`, `task_type`, and `priority`. Must correctly return `total`, `limit`, `offset`, `has_more`, and strictly disjoint items across subsequent pages.
  - `POST /api/v1/tasks/{task_id}/cancel`: Successfully cancels `PENDING`, `QUEUED`, `RUNNING`, or `RETRY_WAIT` tasks (HTTP 200); returns HTTP 404 if task does not exist; returns HTTP 409 Conflict if task is already in terminal state (`SUCCESS`, `DEAD_LETTER`, `CANCELLED`).
  - `POST /api/v1/tasks/{task_id}/retry`: Successfully retries `FAILED` or `DEAD_LETTER` tasks back to `QUEUED` (HTTP 200); returns HTTP 404 if task does not exist; returns HTTP 409 Conflict if task is not in retryable state (`QUEUED`, `RUNNING`, `SUCCESS`).

#### Gate G8.4.2: Multi-Producer Ingestion Storms
* **Requirement:** Measure ingestion throughput, latency distribution, and transactional integrity under three progressive multi-producer load profiles:
  - **Profile G8.4-L1 (Nominal Concurrency):** 100 concurrent producers submitting 1,000 tasks.
  - **Profile G8.4-L2 (High Concurrency):** 500 concurrent producers submitting 5,000 tasks.
  - **Profile G8.4-L3 (Saturation Concurrency):** 1,000 concurrent producers submitting 10,000 tasks.
* **Target Invariants:**
  - 100% of valid submissions return HTTP 201/200.
  - 0 unhandled 500 Internal Server Errors.
  - Strict P50, P95, and P99 latency tracking.
  - 100% parity between rows committed to `tasks` and rows committed to `outbox_events`.

#### Gate G8.4.3: Idempotency Storms & Collision Stress
* **Requirement:** Subject the idempotency subsystem to adversarial collision storms:
  - **Scenario A (Massive Thundering Herd on Single Key):** 100, 500, and 1,000 concurrent threads simultaneously submit the exact same `idempotency_key` with identical payload. Exactly 1 task row must be created in PostgreSQL; 1 thread receives `is_created=True` (HTTP 201), all remaining threads receive `is_created=False` (HTTP 200) returning identical task ID; exactly 1 outbox event.
  - **Scenario B (Key Reuse Matrix):** 100 distinct idempotency keys, each repeated 10 times concurrently across 1,000 requests. Exactly 100 tasks must be created in PostgreSQL.
  - **Scenario C (Conflicting Payload Collision):** Key `K` is submitted with Payload A. A subsequent or concurrent request with Key `K` and Payload B must raise `IdempotencyConflictError` and return HTTP 409 Conflict.

#### Gate G8.4.4: Database Connection Pool Exhaustion & Recovery
* **Requirement:** Evaluate application resilience when database connection demand exceeds pool limits:
  - Configure a constrained engine (`pool_size=10, max_overflow=20`, `pool_timeout=3.0s`).
  - Generate concurrent load exceeding 30 simultaneous database connections.
  - Assert that connections queue cleanly up to `pool_timeout`; if timeout occurs, an informative error is raised rather than a silent deadlock.
  - Once load recedes, verify complete pool recovery: subsequent queries execute immediately with zero leaked connections.

#### Gate G8.4.5: Persistence & Consistency Audit
* **Requirement:** Execute automated direct SQL database consistency verification across all relational tables:
  - `tasks`: 0 null IDs, 0 duplicate idempotency keys, 100% valid state values.
  - `outbox_events`: 100% 1:1 mapping with created tasks, zero orphaned events.
  - `task_attempts`: Monotonic attempt numbering, valid foreign keys referencing existing tasks.
  - `task_results`: Exactly 1 result per completed task, zero orphaned results.
  - `task_events`: Complete audit history matching lifecycle transitions.
