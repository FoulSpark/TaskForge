### 1. Executive Overview & Problem Statement

In distributed asynchronous task processing architectures, worker nodes are fundamentally ephemeral and subject to failure. Workers experience graceful restarts (deployments, auto-scaling down), abrupt terminations (`SIGKILL`, host out-of-memory kills, hypervisor preemption), network partitions causing heartbeat loss, uncooperative handler hangs (infinite loops, socket deadlocks), and heterogeneous workload resource contention.

Milestone **G8.3** evaluates and proves whether TaskForge maintains execution correctness, data durability, and state machine integrity under actual operating system process termination drills and multi-process concurrency.

The central validation question is:
> **Can TaskForge continue processing tasks correctly when workers fail, disappear, restart, or encounter adversarial and heterogeneous workload types?**

---

### 2. Core Functional & Architectural Invariants

TaskForge must guarantee the following invariants under all failure conditions:

1. **At-Least-Once Execution Guarantee:** Every task successfully accepted by TaskForge must reach a valid terminal state (`SUCCESS`, `DEAD_LETTER`, or `CANCELLED`). No task may be permanently stranded in an intermediate state (`QUEUED`, `RUNNING`, `RETRY_WAIT`).
2. **At-Most-Once State Mutation (Idempotence & Fencing):** Exactly one result may be committed per task attempt. A stale worker delayed by network latency, GC pause, or timeout overrun must be fenced cryptographically by `lease_token` and `delivery_token` and strictly prohibited from modifying task status or appending results.
3. **Bounded Recovery Latency:** Tasks abandoned due to worker death or heartbeat loss must be detected and reclaimed within a bounded time window determined by the configured `lease_duration_seconds` and `visibility_timeout_seconds`.
4. **Execution Isolation:** Handlers executing concurrently within worker threads or processes must not leak memory, state, or uncaught exceptions across execution boundaries. A crash or timeout in handler $A$ must not impact or delay handler $B$.

### 3. Detailed Gate Requirements

```
                       TaskForge Worker Subsystem Lifecycle
                       
   [Ready Queue] 
         │ (Atomic Lua claim + delivery_token)
         ▼
   [In-Flight Queue] ──(Crash Point 2: Lost before Lease)──> [Visibility Reaper Reclaims]
         │
         ▼
   [Lease Acquired]  ──(Crash Point 3: Lost before Exec)───> [PostgreSQL Lease Reaper Reclaims]
         │
         ▼
   [Handler Exec]    ──(Crash Point 4: Killed mid-task)────> [Lease Expires & Reclaims]
         │
         ▼
   [Result Persisted]──(Crash Point 5: Killed pre-status)──> [Fenced Lease Integrity Check]
         │
         ▼
   [Message Acked]   ──(Crash Point 6: Killed pre-ack)─────> [Idempotent Delivery Reclaim]
```

#### Gate G8.3.1: Graceful Worker Shutdown
* **Requirement:** When a worker dispatcher receives an OS termination request (`SIGINT` or `SIGTERM`), it must immediately stop polling the broker for new tasks.
* **Drain Invariant:** In-flight tasks already executing on worker threads must be allowed to complete within a configurable `grace_period_seconds`.
* **State Cleanliness:** Tasks completing within the grace period must commit results, transition to `SUCCESS`, release their database lease, and acknowledge their Redis delivery. If any task exceeds the grace period, its lease and in-flight reservation must expire naturally to allow surviving workers to recover it. Zero unaccounted deliveries.

#### Gate G8.3.2: Abrupt Worker Process Termination (Crash Drills)
* **Requirement:** Worker processes must be abruptly killed using operating system process termination (`Popen.kill()` / Win32 `TerminateProcess`) across six discrete points in the execution lifecycle:
  1. **Point 1 (Pre-claim):** Worker killed while idle awaiting broker messages.
  2. **Point 2 (Post-dequeue, Pre-lease):** Worker dequeues message into Redis `in_flight`, then killed before acquiring database lease.
  3. **Point 3 (Post-lease, Pre-handler):** Worker acquires PostgreSQL lease and marks `RUNNING`, then killed before executing handler.
  4. **Point 4 (Mid-handler execution):** Worker killed while handler is actively computing.
  5. **Point 5 (Post-handler, Pre-result):** Handler completes computation, worker killed before calling `TaskRepository.record_result()`.
  6. **Point 6 (Post-result, Pre-ack):** Result is committed in PostgreSQL, worker killed before calling `broker.ack()`.
* **Platform Invariant (Windows 11):** Windows process kills must be performed via real OS subprocesses and explicitly documented as Win32 `TerminateProcess` semantics, distinct from POSIX `SIGKILL`.

#### Gate G8.3.3: Heartbeat Loss, Lease Expiration & Failover
* **Requirement:** Detect worker disappearance when heartbeat ceases.
* **Measurement Parameters:**
  - `heartbeat_interval_seconds`: Nominal rate of worker heartbeat updates to Redis.
  - `lease_duration_seconds`: Window before a PostgreSQL worker lease is deemed expired.
  - `visibility_timeout_seconds`: Window before an unacknowledged Redis message is reclaimed.
  - `failure_detection_latency_ms`: Duration from worker process termination to reaper sweep detection.
  - `recovery_latency_ms`: Duration from reaper sweep to re-enqueue and replacement worker acquisition.
  - `stale_worker_mutation_count`: Must be strictly `0`.

#### Gate G8.3.4: Multi-Process Concurrency & Chaos Under Load
* **Requirement:** Execute a heterogeneous workload across multiple independent OS worker processes sharing the same Redis and PostgreSQL instances.
* **Topology:** 4 independent worker processes, each running 4 execution threads (16 total concurrent execution slots).
* **Workload:** 1,000 tasks randomly distributed across priority levels (P0–P3) and workload handlers.
* **Chaos Drill:** Injected random process terminations (`kill`) at random intervals while producers continuously submit tasks.
* **Verification Invariant:** Zero duplicate results, zero corrupted task states, zero stranded tasks, 100% of tasks terminal in `SUCCESS` or `DEAD_LETTER`.

#### Gate G8.3.5: Heterogeneous Workload Execution Correctness
* **Requirement:** Validate deterministic execution correctness and resource isolation across all registered workload handlers:
  - `noop`: Baseline latency and zero-overhead validation.
  - `cpu_bound`: Intensive prime number computation verifying thread/process CPU contention and accuracy.
  - `io_bound`: Simulated network/disk latency verifying asynchronous thread concurrency without thread pool starvation.
  - `failing`: Intentional exception injection verifying backoff calculation, retry bounds, and dead-letter queue routing.
  - `sleep`: Long-duration execution verifying background lease renewal thread continuity.

#### Gate G8.3.6: Retry, Dead-Lettering & Execution Timeout Non-Blocking Behavior
* **Requirement:**
  1. Tasks exceeding `max_retries` must be definitively marked `DEAD_LETTER` with failure audit attempts.
  2. Handlers exceeding `timeout_seconds` must be aborted. The execution engine must immediately unblock without waiting for uncooperative threads to terminate.
  3. Stale worker write attempts after timeout or lease theft must be trapped and logged with zero database corruption.
