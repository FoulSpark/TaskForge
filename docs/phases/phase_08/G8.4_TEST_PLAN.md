**Environment:** Windows 11 AMD64 / Python 3.12 / PostgreSQL 16 (`taskforge_test`) / Redis 7 (`localhost:6379`)

---

### 1. Verification Strategy & Objectives

Milestone **G8.4** validates the durability, transactional integrity, and resilience of TaskForge's API ingestion boundary and database persistence layer under high concurrency.

The test plan exercises five core gates:
1. **G8.4.1 — API Contract & Edge-Case Audit:** Functional completeness of submission, query, pagination, filtering, cancellation, and retry workflows, verifying standard HTTP status codes (200, 201, 404, 409, 422).
2. **G8.4.2 — Multi-Producer Ingestion Storms:** Multi-threaded stress testing with three load tiers (100 producers / 1,000 tasks; 500 producers / 5,000 tasks; 1,000 producers / 10,000 tasks) profiling latency distributions and outbox consistency.
3. **G8.4.3 — Idempotency Storms & Collision Stress:** Multi-threaded thundering herd on single and multiple idempotency keys, plus conflicting payload validation.
4. **G8.4.4 — Database Connection Pool Exhaustion & Recovery:** Simulating connection starvation against restricted connection pools and verifying graceful queuing and auto-recovery.
5. **G8.4.5 — Persistence & Consistency Audit:** Direct SQL verification of relational tables, foreign key constraints, outbox event parity, and state machines.

### 2. Test Suites Implementation Design

#### Test Suite 1: `test_g84_api_contract.py`
* **Test 1.1 (`test_api_submission_contract`):** Validate valid submissions produce HTTP 201 Created with complete response schema.
* **Test 1.2 (`test_api_validation_errors`):** Submit payloads violating schema constraints (missing fields, invalid priority, negative timeout/retries) and assert HTTP 422 with structured RFC 7807 error details.
* **Test 1.3 (`test_api_task_retrieval_and_not_found`):** Retrieve existing task (HTTP 200) and non-existent UUID (HTTP 404).
* **Test 1.4 (`test_api_pagination_and_filtering_exhaustive`):** Ingest 25 tasks with varied types and priorities. Verify pagination limits (1 to 100), offset boundaries, `total`, `has_more`, disjoint page items, and filter queries (`status`, `task_type`, `priority`).
* **Test 1.5 (`test_api_cancellation_workflow_and_state_guards`):** Cancel queued task (HTTP 200 -> `CANCELLED`); attempt cancellation of non-existent task (HTTP 404); attempt cancellation of terminal task (HTTP 409 Conflict).
* **Test 1.6 (`test_api_retry_workflow_and_state_guards`):** Manually retry dead-lettered task (HTTP 200 -> `QUEUED`, `retry_count=0`); attempt retry on non-existent task (HTTP 404); attempt retry on `QUEUED`/`RUNNING` task (HTTP 409 Conflict).

#### Test Suite 2: `test_g84_ingestion_storms.py`
* **Test 2.1 (`test_ingestion_storm_l1_100_producers_1000_tasks`):**
  - 100 concurrent threads submitting 1,000 distinct tasks.
  - Assert 100% success rate, 0 unhandled exceptions.
  - Calculate P50, P90, P95, P99 latency percentiles and RPS.
  - Verify exactly 1,000 tasks and 1,000 outbox events persisted.
* **Test 2.2 (`test_ingestion_storm_l2_500_producers_5000_tasks`):**
  - 500 concurrent threads submitting 5,000 distinct tasks.
  - Assert 100% success rate, measure throughput and latency profile.
  - Verify exactly 5,000 tasks and 5,000 outbox events persisted.
* **Test 2.3 (`test_ingestion_storm_l3_1000_producers_10000_tasks`):**
  - 1,000 concurrent threads submitting 10,000 distinct tasks.
  - Saturation load test: verify system withstands high producer pressure without transaction corruption.
  - Measure peak RPS and latency degradation.

#### Test Suite 3: `test_g84_idempotency_storms.py`
* **Test 3.1 (`test_thundering_herd_single_key_100_workers`):**
  - 100 concurrent workers submit the exact same idempotency key and identical payload.
  - Invariant: Exactly 1 task row created, exactly 1 outbox event created, all 100 workers return identical task ID.
* **Test 3.2 (`test_thundering_herd_single_key_500_workers`):**
  - 500 concurrent workers submit the exact same idempotency key.
  - Invariant: Exactly 1 task row created, exactly 1 outbox event created, 0 deadlocks.
* **Test 3.3 (`test_key_reuse_matrix_100_keys_10_repetitions`):**
  - 100 distinct keys repeated 10 times concurrently (1,000 requests).
  - Invariant: Exactly 100 tasks created in PostgreSQL.
* **Test 3.4 (`test_idempotency_conflict_rejection`):**
  - Reused key with modified payload or parameters raises `IdempotencyConflictError` (HTTP 409). Original task is untouched.

#### Test Suite 4: `test_g84_pool_exhaustion.py`
* **Test 4.1 (`test_connection_pool_queuing_under_saturation`):**
  - Initialize dedicated engine with `pool_size=5, max_overflow=5, pool_timeout=2.0s`.
  - Launch 25 concurrent database queries.
  - Invariant: Queries queue cleanly; connections return to pool promptly; zero unhandled crashes.
* **Test 4.2 (`test_connection_pool_recovery_after_burst`):**
  - After a pool-saturating burst, verify the engine pool recovers to 0 checked-out connections and subsequent operations execute without latency degradation.

#### Test Suite 5: `test_g84_persistence_audit.py`
* **Test 5.1 (`test_relational_integrity_and_zero_orphans`):**
  - Execute direct SQL queries checking `LEFT JOIN` integrity between `tasks` and `task_attempts`, `task_results`, `task_events`, and `outbox_events`.
  - Invariant: Exactly 0 orphaned child rows.
* **Test 5.2 (`test_outbox_transactional_parity`):**
  - Verify every task in `tasks` has an aggregate event in `outbox_events` with matching payload and metadata.
