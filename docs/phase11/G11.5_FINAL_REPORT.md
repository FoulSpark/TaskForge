## 1. Executive Summary & Architectural Overview

Gate G11.5 establishes the complete execution observability, query inspection, lifecycle management, and operational readiness boundary for TaskForge's Custom Task Definition Registry (Phase 11). Building directly on the foundational execution engine and adapter delivered in Gate G11.4, G11.5 equips operators, platform monitors, and API consumers with the tools necessary to query, inspect, audit, monitor, and cancel custom task definition executions reliably under high concurrency.

Crucially, G11.5 achieves this without creating secondary execution engines, without introducing Prometheus label cardinality explosions, and without compromising the strict lease fencing and immutability guarantees established in earlier gates.

## 3. Detailed Component Architecture & Guarantees

### 3.1 Execution Inspection & Detail APIs (`G11.5-B`)
- **Endpoints**:
  - `GET /api/v1/definitions/{definition_id}/executions`: Paginated list of tasks executed under a definition.
  - `GET /api/v1/definitions/{definition_id}/executions/{task_id}`: Deep inspection returning immutable version snapshots, attempt history, diagnostics, and scrubbed parameters.
- **Tenant Isolation**: Tenant ownership is enforced directly at the SQL query boundary via composite filtering (`Task.definition_id == definition_id`, `Task.tenant_id == tenant_id`). Accessing non-existent definitions or foreign tenant executions returns `404 Not Found`.
- **Deterministic Pagination**: Slices are ordered strictly by `created_at DESC, id DESC`, preventing offset drift or skipped records under rapid insertions.
- **Diagnostics**: Differentiates failure classifications (`SCHEMA_VALIDATION_ERROR`, `OUTPUT_VALIDATION_ERROR`, `HANDLER_UNAVAILABLE`, `TIMEOUT`, `EXECUTION_ERROR`) and reports retry exhaustion.

### 3.2 Bounded Prometheus Telemetry (`G11.5-C`)
- **Zero Cardinality Explosion Contract**:
  - `definition_id`, `task_id`, and `tenant_id` are **strictly forbidden** in Prometheus label dimensions.
  - High-cardinality analysis is delegated entirely to PostgreSQL database queries.
- **Finite Label Bounds**:
  - `task_type`: Governed by `TASK_TYPE_WHITELIST` (`image_resize`, `payment_reconcile`, `report_generate`, `webhook_send`, `csv_export`) with fallback to `other` via `normalize_task_type()`. Max cardinality: 6.
  - `status`: Governed by `STATUS_WHITELIST` (`SUBMITTED`, `SUCCESS`, `FAILED`, `CANCELLED`, `DEAD_LETTER`, `TIMEOUT`, `HANDLER_UNAVAILABLE`). Max cardinality: 7.
  - `phase`: `input` or `output`.
- **Metric Definitions**:
  - `taskforge_definition_executions_total` (`[task_type, status]`): Tracks submission rates and terminal execution states.
  - `taskforge_definition_validation_failures_total` (`[phase, error_type]`): Tracks schema validation boundary failures.
  - `taskforge_definition_handler_unavailable_total` (`[task_type]`): Tracks missing or non-callable handler failures.
  - `taskforge_definition_execution_duration_seconds` (`[task_type]`): Histogram with buckets `(0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0, 10.0, 30.0, 60.0)`.
- **Telemetry Semantics**:
  - `DEFINITION_EXECUTION_DURATION_SECONDS` observes **individual attempt duration** (`duration_ms / 1000.0`), not end-to-end task turnaround latency.
  - Counters increment **strictly after** database transactions commit (`self.db.commit()`), never during read polling or HTTP GET calls.
  - Idempotent submission replays returning existing tasks do **not** double-count submission metrics.
  - All recorder functions are failure-isolated via `try/except` and cannot disrupt task processing.

### 3.3 Audit Event Querying & Deep Recursive Redaction (`G11.5-D`)
- **Endpoint**:
  - `GET /api/v1/definitions/{definition_id}/audit`: Paginated stream of definition lifecycle events filterable by action (`DEFINITION_CREATED`, `VERSION_CREATED`, `VERSION_VALIDATED`, `VERSION_ACTIVATED`, `DEFINITION_EXECUTED`, `DEFINITION_DISABLED`, `DEFINITION_ENABLED`, `EXECUTION_CANCELLED`).
- **Deep Recursive Redaction Engine** (`redact_sensitive_data()`):
  - Traverses nested dictionaries, lists, and metadata structures.
  - Case-insensitive regex matching for sensitive keys (`(api_key|apikey|secret|password|private_key|access_token|bearer_token|authorization|auth_token|token)`).
  - String-level token masking: scans embedded text for `tf_live_[A-Za-z0-9_-]+` and `Bearer <token>`, replacing them with `[REDACTED]`.
  - Lease tokens (`lease_token`, case-insensitive) are stripped unconditionally.
- **Database Immutability**:
  - Redaction is applied strictly to **read projections** returned to API consumers.
  - Underlying database rows in `definition_audit_events` and `tasks` retain their original stored state, ensuring immutable audit evidence is never mutated.

### 3.4 Fenced Cancellation & Version Retention (`G11.5-E` & `G11.5-F`)
- **Endpoint**:
  - `POST /api/v1/definitions/{definition_id}/executions/{task_id}/cancel`: Atomically cancels an active execution.
- **Fenced Cancellation Transaction**:
  - Executed under `SELECT FOR UPDATE` row lock on `tasks`.
  - Non-cancellable/terminal states (`SUCCESS`, `FAILED`, `DEAD_LETTER`, `CANCELLED`) reject cancellation with `409 Conflict`.
  - Clears `lease_token = NULL` and `lease_expires_at = NULL` immediately revoking worker fencing tokens.
  - Transitions all active attempts (`status IN ('RUNNING', 'PENDING')`) to `CANCELLED`.
  - Atomically commits a `STATUS_CHANGED` task event and an `EXECUTION_CANCELLED` definition audit event.
- **Stale-Worker Fencing**:
  - A worker that loses ownership due to cancellation cannot commit success or failure; the database update check (`task.lease_token == lease_token`) affects 0 rows, raises `PermissionError`, increments `FENCING_REJECTIONS_TOTAL`, and rolls back.
  - Exactly zero result, attempt, or status artifacts are persisted by the stale worker.
- **Version Immutability Across Retries & DLQ**:
  - Retrying attempts and terminal `DEAD_LETTER` transitions strictly preserve `(definition_id, definition_version_id)`.
  - Even if an administrator creates and activates Version 2 while a task is in flight or retrying, the execution remains pinned to Version 1 throughout its lifecycle.

## 4. Live PostgreSQL 16 Concurrency Race Matrix

All six critical cancellation race scenarios were verified against live PostgreSQL 16 transactions in `test_g11_postgres_cancellation.py`:

| Concurrency Scenario | Injected Condition | Observed Behavior | Final Database Outcome | Verified |
|:---|:---|:---|:---|:---:|
| **Cancellation vs. Worker Success** | Worker completes during cancellation; attempts commit with revoked lease token. | `TaskRepository.complete_task_success` detects `lease_token != NULL`; raises `PermissionError`. | Task is `CANCELLED`; 0 `TaskResult` rows; 0 artifacts committed. | **PASS** |
| **Cancellation vs. Worker Failure** | Worker fails after cancellation; attempts failure commit with revoked lease. | `TaskRepository.complete_task_failure` detects lease mismatch; raises `PermissionError`. | Task remains `CANCELLED`; failure state rejected. | **PASS** |
| **Cancellation vs. Timeout** | Task times out after cancellation; timeout handler attempts error commit. | Fencing rejects commit; transaction rolls back. | Task remains `CANCELLED`; no contradictory timeout recorded. | **PASS** |
| **Cancellation vs. Retry Scheduling** | User cancels task while in `RETRY_WAIT`. | Task transitions to `CANCELLED`; row lock prevents dispatcher pickup. | Task cannot be reactivated; attempts to queue fail transition validation. | **PASS** |
| **Cancellation vs. Lease Recovery** | Task with expired lease is cancelled right before reaper sweep. | `cancel_task` clears `lease_token = NULL`; reaper ignores non-RUNNING tasks. | Reaper ignores task; zero lease resurrection. | **PASS** |
| **Repeated Cancellation** | Client issues duplicate cancel requests on already cancelled task. | Second call checks `can_cancel_task(CANCELLED)`; raises `DefinitionConflictError`. | Returns `409 Conflict`; no duplicate audit events or counter inflation. | **PASS** |

## 7. Operational Limitations & Scope Boundaries

To preserve strict technical accuracy, the following boundaries are formally recorded:
1. **Scale Envelope**:
   - The verified performance (< 15 ms inspection latency) is established in single-host local and CI environments. Production multi-region deployments with network latency will reflect higher RTTs.
   - Execution listing APIs enforce a maximum limit of `limit=100` items per request.
   - Execution attempt histories are optimized up to 50 attempts per task. Higher attempt volumes should be archived or paginated.
2. **Prometheus Cardinality**:
   - Platform metrics partition only by `task_type` (5 whitelist + `other`) and `status`. Per-definition and per-tenant time-series queries must be served via the database APIs.
3. **Immutability of Freeze Baselines**:
   - Phase 8 (`v0.8.0-phase8-freeze`), Phase 9 (`v0.9.0-phase9-freeze`), and Phase 10 (`v0.10.0-phase10-freeze`) freeze tags remain completely untouched.
   - Database schema migrations are locked at Alembic head `004_g11_definition_registry`.
