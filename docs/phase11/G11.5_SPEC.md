## 1. Purpose, Scope, and Non-Goals

### 1.1 Purpose
Gate G11.5 establishes the operator and client observability boundary for Phase 11 Custom Task Definitions. Building directly on the foundational execution engine and adapter delivered in G11.4, G11.5 equips operators, platform monitors, and API consumers with the tools necessary to query, inspect, audit, monitor, and cancel custom task definition executions reliably under high concurrency.

### 1.2 Scope
1. **Execution Listing & Inspection APIs**:
   - `GET /api/v1/definitions/{definition_id}/executions`: Paginated list of tasks executed under a definition, filterable by status and version.
   - `GET /api/v1/definitions/{definition_id}/executions/{task_id}`: Deep execution inspection returning immutable version snapshot attribution, execution parameters, timeline, full attempt history, failure diagnosis, and output results.
2. **Definition Lifecycle & Validation Query APIs**:
   - `GET /api/v1/definitions/{definition_id}`: Status and active version metadata.
   - `GET /api/v1/definitions/{definition_id}/versions`: Version list.
   - `GET /api/v1/definitions/{definition_id}/versions/{version_number}/validation`: Redacted schema validation diagnostics.
3. **Audit History & Redaction**:
   - `GET /api/v1/definitions/{definition_id}/audit`: Paginated, tenant-scoped audit event stream.
   - Deep recursive redaction of credentials, secrets, authorization headers, and lease tokens.
4. **Execution Observability & Prometheus Metrics**:
   - Zero-cardinality-explosion metric instrumentation tracking submission rates, failure classifications, and handler latency.
5. **Operational Guarantees & Fencing**:
   - Transactional task cancellation respecting database-level lease fencing.
   - Retries and Dead-Letter Queue (DLQ) state transitions strictly preserving `(definition_id, definition_version_id)` attribution.

### 1.3 Non-Goals
- **No Secondary Execution Engine**: Do not introduce alternative queue brokers, worker pools, or runner loops. All executions run through TaskForge's existing worker dispatching, Redis broker, and PostgreSQL state machine.
- **No Arbitrary Code Execution**: Custom definitions remain declarative Draft 2020-12 schemas mapped strictly to registered builtin handlers.
- **No Dynamic Version Mutation**: Historical definition versions remain strictly immutable.

## 4. API Contracts and Response Schemas

### 4.1 `GET /api/v1/definitions/{definition_id}/executions`
List executions for a definition within the caller's tenant.

- **Query Parameters**:
  - `status`: Optional `TaskStatus` filter (e.g. `QUEUED`, `RUNNING`, `SUCCESS`, `FAILED`, `CANCELLED`, `DEAD_LETTER`).
  - `version_number`: Optional `int` filter matching definition version number.
  - `limit`: `int` (1..100, default 50).
  - `offset`: `int` (>= 0, default 0).
- **Ordering**: Deterministic `created_at DESC, id DESC`.

### 4.3 `POST /api/v1/definitions/{definition_id}/executions/{task_id}/cancel`
Cancels an active or queued execution under strict lease fencing.
- **Response `200 OK`**: Returns updated task response in `CANCELLED` status.
- **Response `409 Conflict`**: If task is already in terminal state (`SUCCESS`, `FAILED`, `DEAD_LETTER`, `CANCELLED`).

## 5. Database Queries & Tenant Isolation

### 5.1 Enforcing Tenant Ownership at DB Query Level
Tenant filtering is never deferred to Python application code. All queries include `tenant_id` in their `WHERE` predicates:

```python
# Listing executions:
stmt = (
    select(Task)
    .join(TaskDefinitionVersion, Task.definition_version_id == TaskDefinitionVersion.id)
    .where(
        Task.definition_id == definition_id,
        Task.tenant_id == tenant_id,
    )
)
if status:
    stmt = stmt.where(Task.status == status)
if version_number:
    stmt = stmt.where(TaskDefinitionVersion.version == version_number)

stmt = stmt.order_by(desc(Task.created_at), desc(Task.id)).offset(offset).limit(limit)
```

### 5.2 Distinguishing 404 Not Found vs. Cross-Tenant Denial
1. Query definition by `(definition_id, tenant_id)`. If missing $\rightarrow$ `404 Not Found` (avoids leaking existence of other tenants' definitions).
2. Query task by `(task_id, definition_id, tenant_id)`. If missing $\rightarrow$ `404 Not Found`.

## 6. Metrics and Observability Design

### 6.1 Bounded Cardinality Architecture
> [!IMPORTANT]
> Putting raw `definition_id` or `task_id` into Prometheus label dimensions causes catastrophic label cardinality explosion in high-scale multi-tenant clusters.

**Rule for Prometheus Metrics in G11.5**:
- Raw `definition_id` is **never** used as a Prometheus label dimension.
- Per-definition analytics are queried via the database (`GET /api/v1/definitions/{id}/executions`).
- Prometheus metrics track platform-level aggregations partitioned strictly by `task_type`, `execution_type`, `phase`, and `status`:

```python
DEFINITION_EXECUTIONS_TOTAL = Counter(
    "taskforge_definition_executions_total",
    "Total count of custom task definition executions submitted or processed",
    ["task_type", "status"],  # e.g. task_type="webhook_send", status="SUCCESS"
)

DEFINITION_VALIDATION_FAILURES_TOTAL = Counter(
    "taskforge_definition_validation_failures_total",
    "Total validation errors on custom definition boundaries",
    ["phase", "error_type"],  # phase="input"|"output", error_type="SCHEMA_VALIDATION_ERROR"
)

DEFINITION_HANDLER_UNAVAILABLE_TOTAL = Counter(
    "taskforge_definition_handler_unavailable_total",
    "Total executions failing due to uncallable or missing live registry handlers",
    ["task_type"],
)

DEFINITION_EXECUTION_DURATION_SECONDS = Histogram(
    "taskforge_definition_execution_duration_seconds",
    "Execution duration of custom definition tasks in seconds",
    ["task_type"],
    buckets=(0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0, 10.0, 30.0, 60.0),
)
```

### 6.2 Counter Increment Guarantees
- Counters increment **only** on verified state transitions in `TaskRepository` or `execution_engine.py`, never during read-only polling, HTTP GET inspections, or health checks.
- Duration histograms observe elapsed execution time strictly on terminal attempt completion.

## 7. Audit Events and Recursive Redaction

### 7.1 Recursive Redaction Engine
A centralized, recursive utility `redact_sensitive_data(payload)` strips secrets across nested dicts, lists, and JSON strings:
- **Key Matching**: Any key matching `(api_key|secret|password|private_key|access_token|bearer_token|authorization|token)` (case-insensitive) is replaced with `"[REDACTED]"`.
- **Value Matching**: Any string matching regex signatures for standard credentials (e.g. Bearer tokens, private keys) is masked.
- **Lease Tokens**: Fields named `lease_token` are stripped unconditionally from all client-facing models.

### 7.2 Audit Log Integrity (G11.4-12)
All definition events (`DEFINITION_CREATED`, `VERSION_CREATED`, `VERSION_VALIDATED`, `VERSION_ACTIVATED`, `DEFINITION_EXECUTED`, `DEFINITION_DISABLED`, `DEFINITION_ENABLED`, `EXECUTION_CANCELLED`) are stored in `definition_audit_events` with:
- Tenant isolation (`tenant_id`).
- Identity attribution (`actor_id`).
- Monotonic timestamps.
- Redacted `metadata_json`.

## 8. Cancellation, Timeout, Retry, and Fencing Semantics

### 8.1 Fenced Cancellation Flow
```mermaid
sequenceDiagram
    participant Client
    participant API as Route / Service
    participant DB as PostgreSQL
    participant Worker as Stale Worker

    Client->>API: POST /definitions/{id}/executions/{task_id}/cancel
    API->>DB: SELECT Task FOR UPDATE WHERE id=:id AND tenant_id=:tenant_id
    alt Task is Terminal (SUCCESS/FAILED/DEAD_LETTER)
        DB-->>API: Status is terminal
        API-->>Client: 409 Conflict ("Task in terminal state cannot be cancelled")
    else Task is Active/Queued (QUEUED/RUNNING/RETRY_WAIT)
        API->>DB: UPDATE tasks SET status='CANCELLED', lease_token=NULL, lease_expires_at=NULL
        API->>DB: UPDATE task_attempts SET status='CANCELLED' WHERE status='RUNNING'
        API->>DB: INSERT TaskEvent ('STATUS_CHANGED', 'CANCELLED')
        API->>DB: COMMIT
        API-->>Client: 200 OK (Task cancelled)
    end

    Note over Worker,DB: Stale Worker attempts completion
    Worker->>DB: UPDATE tasks WHERE id=:id AND lease_token=:stale_token
    DB-->>Worker: 0 rows updated
    Worker->>DB: ROLLBACK
    Note over Worker: Fencing rejection logged; zero artifacts written
```

### 8.2 Retries and Dead-Letter Preservation
- When a task fails with retryable error (`HANDLER_EXECUTION_ERROR`, `TIMEOUT`), retry scheduling preserves the original `(definition_id, definition_version_id)`.
- When retries are exhausted (`retry_count >= max_retries`), the state transitions `RUNNING -> FAILED -> DEAD_LETTER`. The task continues to reference the immutable `definition_version_id` for auditability.

## 9. Error Handling and Compatibility

- Consistent RFC-7807 compliant error envelopes:
  `{"error": {"code": "HTTP_404", "message": "...", "details": null, "correlation_id": "..."}}`
- `404 Not Found`: Missing definitions or tasks outside tenant scope.
- `409 Conflict`: Invalid state transitions (e.g. cancelling completed tasks, executing disabled definitions).
- `422 Unprocessable Entity`: Invalid query parameters or schema validation failures.

---

## 10. Security and Performance Considerations

1. **Denial of Service & Large Attempt History**:
   - Limit attempt listing to maximum 50 attempts per task; paginate timeline events.
   - Restrict execution list queries to `limit <= 100`.
2. **Database Indexing**:
   - Verified compound index on `tasks(definition_id, tenant_id, created_at DESC)`.
   - Foreign key indexing on `tasks(definition_version_id)`.
3. **Connection Pool Protection**:
   - Read-only inspection queries run in short-lived sessions without holding row locks.

## 13. Risks, Unresolved Decisions, and Rollback Strategy

- **Risk**: Stale worker commits result after user triggers cancellation.
  - *Mitigation*: Conditional SQL update checks `lease_token`. Cancellation sets `lease_token = NULL`, causing any subsequent worker update to affect 0 rows and trigger rollback.
- **Risk**: Prometheus label cardinality blowup.
  - *Mitigation*: Strictly omit `definition_id` from Prometheus labels; report per-definition counts through database APIs.
- **Rollback**: G11.5 is purely additive; can revert directly to `f500819` baseline without breaking core task execution.
